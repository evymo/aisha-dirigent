# AISHA Dirigent → Claude app (auto-convertible pipeline)

> **Status (2026-06-21):** Implemented end-to-end. One source of truth (the MCP
> server) is auto-converted into **both** Claude install formats: a Claude Code
> plugin and a Claude Desktop Extension (`.mcpb`). Generated via the existing
> `gen:ide` adapter registry; packaged with a zero-dependency builder.
>
> Companion: [dirigent-overlay-pipeline.md](../architecture/dirigent-overlay-pipeline.md)
> (the `.claude/*` supervision overlay — a sibling adapter).

## Proč (why)

The VS Code (`extensions/aisha-dirigent/`) and Zed (`extensions/aisha-dirigent-zed/`)
extensions give AISHA Dirigent a home in those editors. Claude Code and Claude
Desktop need the **same governance surface** — rules, seed/merge tracking, model
routing, health, local-LLM cost/usage — as a first-class, installable app. Rather
than maintain a third hand-written port, we **auto-convert**: a single MCP server
defines the capabilities, and an adapter emits the packaging for both Claude
formats from that server's own declared surface. The package can never drift from
the code.

## Outputs (two formats, one source)

```
extensions/aisha-dirigent-claude/
├── server/                         ← hand-written, zero-dependency MCP server (SOURCE OF TRUTH)
│   ├── index.mjs                   ← MCP stdio protocol + `--list-tools` introspection
│   ├── tools.mjs                   ← read/status surface (15 tools, 3 resources)
│   ├── compose.mjs                 ← write-capable composition tools (3) — author .claude/* artifacts
│   ├── lib.mjs                     ← workspace resolution + safe fs/exec/http/write
│   └── hook-session-context.mjs    ← SessionStart context injector
│
│   ── generated by the adapter (do not edit by hand) ──
├── manifest.json                   ← Claude Desktop Extension (MCPB spec 0.3)
├── .claude-plugin/plugin.json      ← Claude Code plugin manifest
├── .mcp.json                       ← Claude Code MCP wiring
├── package.json                    ← bundle metadata (no deps)
├── commands/<tool>.md              ← 1 slash command per MCP tool
├── skills/aisha-dirigent/SKILL.md  ← operating skill + editor-parity table
├── agents/aisha-dirigent.md        ← read-only governance advisor subagent
├── hooks/hooks.json                ← SessionStart hook
├── icon.png                        ← copied from the VS Code extension at package time
└── README.md
```

The MCP **Bundle** (`.mcpb`) is written to `dist/claude-app/aisha-dirigent.mcpb`.

## Pipeline

```
┌──────────────────────────────────────────────────────────────────────────┐
│ SOURCE OF TRUTH                                                            │
│   extensions/aisha-dirigent-claude/server/  (tools.mjs → TOOLS, RESOURCES) │
│   $ node server/index.mjs --list-tools   → JSON surface                    │
│                                                                            │
│   extensions/aisha-dirigent/package.json (contributes.chatParticipants)    │
│     → editor-parity table (traceability of the conversion)                 │
└───────────────┬────────────────────────────────────────────────────────── ┘
                │
                ▼
┌──────────────────────────────────────────────────────────────────────────┐
│ ADAPTER  scripts/ide-adapters/adapter-claude-app.mjs                       │
│   registered in registry.mjs as `claude-app` (multiFile)                   │
│   maps:  tool → manifest.tools[]  +  tool → commands/<slug>.md             │
│          tools → SKILL.md table   +  tools → agent allow-list              │
└───────────────┬───────────────────────────────────────────┬────────────── ┘
                │ (a) via gen:ide                             │ (b) via packager
                ▼                                             ▼
   npm run gen:ide -- --format=claude-app          npm run package:claude-app
   (ruleset payload from backend/cache)            (offline: writes files,
   writes the packaging layer                       copies icon, validates,
                                                     zips → dist/.../*.mcpb)
```

Two entry points share the **same** `adapter.generate()`:

- **`gen:ide`** — the canonical regeneration, alongside `CLAUDE.md`, `.cursorrules`,
  the claude-overlay, etc. Uses the AISHA ruleset payload (needs backend or a
  cached `--offline` payload).
- **`package:claude-app`** — self-contained, no backend required. Regenerates the
  packaging layer, validates the manifests, and builds the installable `.mcpb`.

## Commands

```bash
# Regenerate the packaging layer (canonical, via the gen:ide registry)
npm run gen:ide -- --format=claude-app          # or: npm run gen:claude-app
npm run gen:claude-app:offline                  # use cached ruleset payload

# Build the installable Claude Desktop Extension (offline-capable)
npm run package:claude-app                       # → dist/claude-app/aisha-dirigent.mcpb
npm run package:claude-app:check                 # validate only (CI gate)

# Tests (adapter + server protocol + zip packer)
npm run test:claude-app
```

## Install

**Claude Code (marketplace)** — the repo ships `.claude-plugin/marketplace.json`,
so it installs in one step from a clone or the git host:

```bash
claude plugin marketplace add evymo/aisha-dirigent   # or: add ./ (local clone)
claude plugin install aisha-dirigent@evymo
```

**Claude Code (local dev)** — install the plugin directory directly:

```bash
claude plugin install ./extensions/aisha-dirigent-claude
```

The plugin's `.mcp.json` launches the server with
`AISHA_WORKSPACE=${CLAUDE_PROJECT_DIR}`, so it reads the project you have open.

**Claude Desktop (.mcpb)** — run `npm run package:claude-app`, then install
`dist/claude-app/aisha-dirigent.mcpb` (double-click, or Settings → Extensions),
or download it from a release (see below). On install, Claude Desktop prompts for
the **AISHA workspace** directory, passed to the server as `AISHA_WORKSPACE`.

## Release

`.forgejo/workflows/claude-app-release.yml` builds and publishes the `.mcpb` on a
dedicated tag (so the Claude app releases independently of the monorepo version):

```bash
git tag claude-app-v0.6.1 && git push --tags
```

The workflow runs the zero-dep `test:claude-app` gate, builds + validates the
bundle (`scripts/package-claude-app.mjs`), emits a `.sha256`, uploads the build
artifact, and attaches `aisha-dirigent.mcpb` to the release for that tag. No
`npm ci` is required — the app + packager are Node-stdlib only.

## Capability surface

Status/read tools are side-effect free. The **composing** tools
(`aisha_sync_instructions`, `aisha_compose_overlay`, `aisha_scaffold`) **write
only when `apply=true`** — they preview/dry-run otherwise (Principle of Least
Privilege). Composition is **backend-parameterized**: `aisha_compose_overlay`
drives `gen:ide`, which pulls the ruleset + `claude_hook_bindings` for the active
story/domain and emits exactly the artifacts that fit the project. Everything
operates on local `.aisha/`, `.claude/`, and git state; nothing leaves the machine.

| Group | Tools |
| --- | --- |
| Seed / merge tracking | `aisha_seed_status`, `aisha_merge_status`, `aisha_db_convergence` |
| Rules / IDE sync | `aisha_active_rules`, `aisha_ruleset`, `aisha_sync_instructions` |
| Session / story | `aisha_session`, `aisha_story`, `aisha_decisions`, `aisha_feed` |
| Routing / models / cost | `aisha_route`, `aisha_models`, `aisha_cost_usage` |
| Health / environment | `aisha_health`, `aisha_scan_env`, `aisha_bringup` |
| **Composition (write)** | `aisha_overlay_plan`, `aisha_compose_overlay`, `aisha_scaffold` |

`aisha_bringup` starts the local AISHA stack via the shared entry-point
`npm run stack:bringup` when no backend is reachable (pass `dryRun: true` to see
the command without starting anything). The command + JSON status parsing are the
single source of truth in `scripts/lib/bringup-contract.mjs`; the server inlines a
copy (it ships standalone in the `.mcpb`) and a **drift gate**
(`scripts/ide-adapters/__tests__/claude-app-drift.test.mjs`) fails CI if the copy
diverges — the same gate guards the duplicated `mergeSettingsJson`.

Resources: `aisha://session`, `aisha://rules`, `aisha://config`.

### Composition — how the backend parameterizes the project

```
aisha_overlay_plan        → preview: which Claude artifacts + hook bindings the
                            backend would emit for this story/domain (read-only)
aisha_compose_overlay     → runs gen:ide --format=claude-overlay|claude|claude-app
   apply=false (default)    dry-run; apply=true writes .claude/* (backend-driven)
aisha_scaffold            → author one tailored skill|hook|command|agent into
   apply=false (default)    .claude/ (+ settings.json merge for hooks); preview
                            unless apply=true
```

The backend (ruleset + `claude_hook_bindings`, keyed to story/domain) decides
*what* fits the project; these tools *apply* it. Ad-hoc artifacts go through
`aisha_scaffold`, pre-filled with project context (domain, active rule categories).

## Extending

1. Add a tool (`{ name, title, description, inputSchema, handler }`): read/status
   tools go in `server/tools.mjs` (`TOOLS`); write/compose tools go in
   `server/compose.mjs` (`COMPOSE_TOOLS`, gated behind `apply`).
2. Run `npm run package:claude-app` — the new tool automatically appears in
   `manifest.json`, gets a `commands/<slug>.md`, and is listed in the skill +
   agent allow-list. No manifest editing required.
3. `npm run test:claude-app` (node:test) and `npm run test:scripts` (vitest) to verify.

## Design notes

- **Zero runtime dependencies.** The server hand-rolls MCP stdio JSON-RPC (mirrors
  `extensions/aisha-dirigent/src/mcp-client.ts`), and the packer (`scripts/lib/mini-zip.mjs`)
  writes the zip with `node:zlib` only. The `.mcpb` ships no `node_modules`.
- **`--list-tools` introspection** keeps the manifest in lock-step with the server;
  the adapter never hard-codes the tool list.
- **Versioning** is inherited from the VS Code Dirigent extension
  (`extensions/aisha-dirigent/package.json`) so all Dirigent surfaces move together;
  override with `AISHA_CLAUDE_APP_VERSION`.
