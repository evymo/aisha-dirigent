## `entrypoint:`

### Proč pojistka na prázdné heslo stojí TADY, a ne v compose

Do 2026-08-16 stálo v `environment:` čtyřikrát `${REDIS_PASSWORD_X:?…}`. Vypadá
to jako správná fail-closed pojistka — a jako pojistka to i fungovalo. Jenže
`${VAR:?}` je požadavek na PARSOVÁNÍ compose, a Coolify parsuje celý soubor
DVAKRÁT: jednou při buildu (jen s `build-time.env`, tedy s klíči, které mají
`is_buildtime=true`) a podruhé při spuštění. Aby build neumřel na
„required variable REDIS_PASSWORD_CORE is missing a value", musela ta čtyři
hesla dostat build-time příznak — a Coolify build-time hodnoty posílá jako
`--build-arg` a vkládá `ARG <KEY>` za každý `FROM`. Tím se zapečou do metadat
obrazu a `docker history` je vydá komukoli, kdo na obraz dosáhne, napořád.

Pojistka na prázdné heslo tedy platila cenou v podobě trvale vystaveného hesla.

Otázka, na kterou se `${VAR:?}` ptal, přitom byla „dorazila hodnota?". Tu dnes
zodpovídá `scripts/coolify-sync-envs.sh` přímo tam, kde se doručuje: po zápisu
si envy přečte zpátky a na prázdném tajemství skončí červeně. To je bližší
stanoviště i dřívější okamžik.

Zbylo druhé riziko, které read-back nepokryje: kontejner může dostat prázdnou
hodnotu z jiného důvodu (ruční zásah v Coolify UI, jiný zdroj env). Ta hodnota
tu jde do souboru ACL — `user core on >… ~* &* +@all` — a prázdné heslo z toho
udělá řádek, jehož význam určí až parser Redisu. Co udělá, není náš kontrakt;
hláška by byla nesrozumitelná a v horším případě by uživatel vznikl s heslem,
které nikdo nezná. Proto smyčka na začátku entrypointu: ptá se na hodnotu,
kterou kontejner SKUTEČNĚ dostal, ve chvíli, kdy na ní záleží, a padá s
hláškou, která říká, kde hodnota vzniká a kdo ji doručuje.

Souhrn: `${VAR:?}` → `${VAR}` v `environment:` (prázdno tam parse toleruje,
protože build-parse a up-parse jsou dva různé běhy), a fail-closed vlastnost
zůstala — jen o jedno patro níž, kde nic nezapéká.

Generate ACL file on startup, then exec redis-server with it.
Keys: core=*, langfuse=lf:*, n8n=bull:* + n8n:*

## `test: ["CMD", "redis-cli", "ping"]`

Auth-less liveness: redis-cli ping exits 0 on ANY server reply (incl.
NOAUTH — verified) and 1 only when the server is unreachable. NEVER
interpolate the password here: parse-time ${VAR} bakes it into
Healthcheck.Test (docker inspect / Coolify UI leak) and the $$-form
breaks under Coolify (COOLIFY_COMPOSE_RULES.md §3).

## `test: ["CMD-SHELL", "redis-cli --no-auth-warning -u redis://core:$${REDIS_PASSWORD_CORE}@127.0.0.1:6379 ping | grep -q PONG"]`

The ACL above sets `user default off`, so an UNAUTHENTICATED `redis-cli ping`
answers NOAUTH and the probe can never pass — the container is reported
unhealthy while the server logs "Ready to accept connections". shared-redis
is wave 1, so that permanently gate-blocked every dependent app (measured
2026-08-11: 23 apps aborted behind it).

Authenticate as `core`, which the ACL grants an explicit `+ping` — least
privilege, and it fails loudly if that grant is ever dropped. CMD-SHELL so
the container's own env expands; --no-auth-warning keeps the password off
stderr. `grep -q PONG` because redis-cli exits 0 even on an error reply.
