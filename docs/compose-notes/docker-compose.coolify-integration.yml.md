# docker-compose.coolify-integration.yml — notes

Prose extracted from `docker-compose.coolify-integration.yml` by `scripts/compose-extract-notes.mjs`.
The compose file is passed to Coolify as a command-line argument and competes
with ARG_MAX, so it carries configuration only.

## `x-common: &common`

docker-compose.coolify-integration.yml

Integration stack: Alquist Insight (Ragnarok RAG + Maestro dialog) + Elasticsearch + RabbitMQ
Deployed on Backend as aisha-backend (separate from core AISHA services on Frontend).

Insight stack composition:
  - Ragnarok (port 9696) — hybrid retrieval (Elasticsearch BM25 + KNN)
  - Maestro  (port 8020) — multi-turn dialog management (Alexa Prize USP)
  - Elasticsearch (9200) — shared vector backend
  - Kronos NOT integrated — AISHA RPC layer (knowledge_items + story_rulesets) replaces it.

Maestro is invoked via `services/svc-ai-chat` orchestrace as a LLM provider adapter.
Frontend NEVER calls Maestro directly — Tao/Psyche/Hippocampus/governance vrstvy
se aplikují v svc-ai-chat, ne uvnitř Maestra. See docs/INSIGHT_INTEGRATION.md.

NOTE: Keycloak moved to aisha-admin stack (docker-compose.coolify-admin.yml on Frontend)

NetBird mesh (cross-server) — stav od 2026-09-17, BEZ host portů:
netbird-agent má vlastní netns (mesh IP), sdílí ji `integration-mesh-ingress`
(Caddy, HTTP podle Host) a `integration-mesh-tcp` (nginx stream, TCP).
Adresy konzumentů ODVOZUJE katalog (config/services.json → integration) a
doručuje env-doktor — nic se nenastavuje ručně:
  RAGNAROK_URL=http://<prefix>-integration.<mesh>:9696   (ingress)
  MAESTRO_URL=http://<prefix>-maestro.<mesh>:8020        (ingress)
  RABBITMQ_HOST=<prefix>-integration.<mesh>, RABBITMQ_PORT=5672 (TCP sidecar)
⛔ Do 2026-09-17 compose publikoval 9696/8020/5673 na 0.0.0.0 hostitele: pevný
nárok na sdíleném hostiteli (druhá instance téže platformy na giah držela
5673 a 8020 → stack se nenasadil) a cesta mimo edge.

Coolify UI setup:
- Docker Compose source: docker-compose.coolify-integration.yml
- Environment Variables: RAGNAROK_API_KEY, MAESTRO_API_KEY, ELASTIC_PASSWORD,
  OPENAI_API_KEY, INSIGHT_LLM_BACKEND (default OpenAI; vLLM opt-in),

## `pki-init:`

─────────────────────────────────────────────
pki-init — bakes AISHA CA bundle into pki-certs volume.
NetBird agent uses /certs/pki/aisha-ca-bundle.pem to trust the
AISHA PKI cert presented by the netbird-internal-tls caddy sidecar
on the mesh-internal path (netbird.mesh.aisha.internal:33073).
─────────────────────────────────────────────

## `PKI_BRIDGE_URL: ${PKI_BRIDGE_URL:-}`

Referencing PKI_BRIDGE_URL makes coolify-sync-envs push it here so we can
fetch the LIVE realm CA bundle (the baked one goes stale vs the running CA).

## `command: ["/usr/local/bin/assemble-ca-bundle.sh"]`

Assembles the mesh trust bundle (system roots + LIVE-or-baked AISHA realm
CAs). Baked into Dockerfile.pki-init so all 3 mesh stacks share one impl.

## `test: ["CMD-SHELL", "curl -s -o /dev/null -w '%{http_code}' http://localhost:9200/ | grep -qE '^(200|401)$'"]`

Auth-less liveness: with xpack security enabled ES answers 401 before
cluster health is even computed — 200|401 proves the HTTP layer is up.

into Healthcheck.Test (visible in docker inspect / compose config /
Coolify UI), and the $$-deferred form is banned by
docs/deploy/COOLIFY_COMPOSE_RULES.md §3 (Coolify double-quoting).

## `OPENAI_KEY: ${AISHA_LLM_GATEWAY_KEY:-}`

Route insight's "OpenAI" provider through AISHA llm-gateway. The
daemon is OpenAI-compatible at /v1/* (chat.completions, embeddings,
models — verified 2026-05-24: GET /v1/models returns 200 internally
against `http://llm-gateway:4000`). Bearer = AISHA_LLM_GATEWAY_KEY
(the service-side token that llm-gateway expects; populated by
cold-start). This means:
  - llmRouter / soulforge / llmgateway.io upstream owns model
    selection; insight just makes "OpenAI" calls and gets routed
  - we never have to give Ragnarok / Maestro a real OpenAI key
  - operator can still override INSIGHT_OPENAI_ENDPOINT to point
    anywhere else (Azure OpenAI, vLLM, direct OpenAI)

## `KRONOS_API_KEY: "not-integrated-aisha-rpc-replaces-it"`

Kronos data layer NOT integrated — AISHA RPC + aisha-kronos-shim ho nahrazuje.

## `test: ["CMD-SHELL", "wget -qO- http://127.0.0.1:9625/health >/dev/null 2>&1 || exit 1"]`

kronos-shim listens on 9625 (PORT env + expose above); 9696 is RAGNAROK's

## `- netbird-backend-data-v3:/var/lib/netbird`

NetBird 0.70+ persists agent identity in /var/lib/netbird/default.json,
NOT /etc/netbird. Mount the SAME named volume at both paths (edge
mesh-router pattern). Without this, every restart re-enrolls with a fresh
WireGuard key → duplicate peers → Signal rejects streams. See H-N3 in
docs/audit/2026-07-07-repo-audit-a-z.md.

## `extra_hosts:`

Internal mesh path: agent on Backend → Frontend LAN IP:33073 (caddy sidecar
in netbird stack with AISHA PKI cert). With network_mode: host, agent
uses Backend's eth0 directly → LAN switch → Frontend eth0:33073. Trust via
mounted aisha-ca-bundle.pem (NB_SSL_TRUST_BUNDLE).

NETBIRD_MGMT_HOST fallback uses Docker's `host-gateway` magic value
(matches working frontend-core pattern in docker-compose.coolify.yml).
If the integration stack deploys to a DIFFERENT physical host than
netbird-mgmt, operator overrides NETBIRD_MGMT_HOST=<Frontend LAN IP>
in Coolify env. Same-host deploy works without override via
host-gateway resolution. Was previously `:?` (required, hard-fail)
which broke every fresh deploy of this stack on a Coolify project
where the operator hadn't manually wired the env var.

## `pki-certs:`

AISHA PKI cert bundle volume (populated by pki-init from baked CA).

## `netbird-backend-data-v3:`

Volume name bumped to v3 — see docker-compose.coolify-netbird.yml comment.

## `internal:`

Both `internal` and `coolify` alias the external coolify network — avoid
per-stack bridges (Docker default address pool exhaustion).

## `cpus: ${INTEGRATION_ES_CPUS:-2.0}`

OOM guard (incident 2026-07-24): heap is capped below (-Xmx2g) but ES also
uses large off-heap/direct buffers + mmap; without a container mem_limit its
RSS can grow well past the heap and, on a shared backend host, contribute to
a host-wide OOM. Cap the container ~heap+off-heap headroom.

## `cap_add:`

Bridge mode, NE network_mode: host — vlastní netns, jak to má core,
local-ingest, potok i edge ("Bridge mode — own netns, no host daemon
conflict"). V hostitelském namespace agent NEMÁ vlastní wt0, vidí to
hostitelské: měřeno 2026-07-28 hlásily backend-integration i
experimental-cosmos TÉŽE rozhraní (ifindex 6083) a TUTÉŽ adresu
100.103.31.228, zatímco management DB jim přidělila různé
(.31.228 vs .15.146). Jeden agent vyhrál, druhý tiše jel na cizí
identitě. Ani jeden z těchhle dvou stacků nemá mesh-ingress, takže
hostitelský režim jim nic nedával — jen bral vlastní identitu.

## Bez host portů (2026-09-17)

`ragnarok`, `maestro` a `rabbitmq` do 2026-09-17 publikovaly `9696:9696`,
`8020:8020` a `5673:5672` na 0.0.0.0 hostitele. Pevný port je nárok na
SDÍLENÉM hostiteli a cesta mimo edge. Naměřeno na giah: stack integration jiné
instance téže platformy držel 5673 a 8020 → nasazení skončilo „Bind for
0.0.0.0:5673 failed: port is already allocated" a vlna 8 cold-startu se
zastavila. Mesh cestu přes host port zrušil už 6e631ee7c (agent má vlastní
netns), takže port nikomu nesloužil.

Dnes: HTTP (ragnarok, maestro) rozvádí `integration-mesh-ingress` podle Host,
AMQP `integration-mesh-tcp` (nginx stream, vzor `clamav-mesh-tcp`) — oba v netns
agenta. Tabulky, `RABBITMQ_HOST` i `RABBITMQ_PORT` odvozuje katalog
(`integration.internal_tcp_endpoints`, `port_env_aliases`) a doručuje env-doktor.
Cíl TCP trasy je alias `<prefix>-integration--rabbitmq` (container_name Coolify
přepisuje). Hlídá brána `tcp-port-na-hostiteli`.
