# Schema Relationship Lens — the "DB architect" tool

> A relationship/foreign-key lens over the applied schema: **where are the
> relationships ("vazby") enforced, and where are they not?** Built as a *lens
> over existing signals* (the cold-start apply harness + the `pg_constraint`
> catalog), not a new subsystem, and not a hand-drawn diagram tool.

## Why this shape (and why not a GUI modeler)

This repo's database is **generated from a source-of-truth** (`aisha/db/sql/` →
`00000000000000_baseline.sql`) and guarded by **gates against an applied
catalog** (`verify-cold-start-apply.sh`). In a generate-from-SoT world the
relationship picture must be a **projection of the schema, recomputed**, never a
hand-maintained artifact that drifts the moment it's drawn. That rules out
GUI/CASE modelers (e.g. drawing tools, OntoUML/DEMO editors): they produce
hand-maintained models on the wrong side of the generated-vs-authored line that
defines this codebase. So the lens is two generated halves:

| Half | Artifact | Runs on | Role |
| --- | --- | --- | --- |
| **Enforce** | `scripts/db/check-fk-relationship-gaps.mjs` + `src/tests/gates/fk-relationship-gaps.allowlist.json` | cold-start applied catalog (`verify-cold-start-apply.sh` step 5/5) | fails on a **new** unenforced `*_id` relationship |
| **Visualize** | `scripts/db/generate-schema-docs.mjs` → `docs/db/RELATIONSHIPS.md` (+ optional full `tbls` site) | any applied schema (psql) | per-domain ER diagram + unenforced-gap table |

It deliberately mirrors the two sibling DB-security invariants
(`check-definer-rpc-security.mjs`, `check-rls-self-reference.mjs`): catalog-read,
identity-keyed allowlist, `--report` mode, same `verify-cold-start-apply.sh`
home. Same pattern, third invariant.

## The gate: enforce relationship hygiene

**What it flags.** A `public` base-table column named like a foreign key
(`*_id`, not the PK `id`, not itself a PK) with **no FK constraint** covering it
— but only when a **high-precision signal** says it should be a relation (else
it's almost certainly not one, e.g. `external_id`/`correlation_id`/`trace_id`):

- **`fk-elsewhere`** — a same-named column backs a real FK on *another* public
  table → inconsistent enforcement (the textbook missing constraint).
- **`stem-table`** — a public table named `<stem>` or `<stem>s` exists (stem =
  column minus `_id`), and it isn't the column's own table (the
  `stripe_disputes.stripe_dispute_id` external-ID pattern is excluded).

**Why catalog, not regex over `aisha/db/sql/tables/*.sql`.** Truth = the applied
constraint set, including deferred FKs in `aisha/db/sql/constraints/` and any
added by a later migration. Only the catalog knows the post-apply shape — and
`pg_constraint contype IN ('f','p')` distinguishes FK targets / PK columns
authoritatively, where a regex over 338 files would be fragile.

**Identity-keyed snapshot, not a count.** A new gap is a new `table.column`
identity = a hard fail. Pre-existing gaps are snapshotted into the allowlist
(`--baseline`) — exactly like `gate:branding:baseline` /
`gen-workaround-markers-baseline`. The gate then guards **regressions**; the
architect drives the snapshot down over time by adding real FKs.

### Findings at first baseline (2026-06-02)

Against the applied cold-start schema (**364** public base tables):

- **205** `*_id` columns with no FK constraint;
- of those, **77** high-confidence candidate gaps (128 ignored as no-signal);
- snapshotted into `fk-relationship-gaps.allowlist.json`.

Concrete example — `story_id → partner_stories` is enforced in `story_entries`,
`story_contexts`, … but **not** in `story_environments`, `story_rulesets`,
`lab_test_orders`, `moderation_sessions`, `openclaw_notifications`. That
inconsistency is exactly what the lens surfaces.

## The docs: visualize relationships per domain

`docs/db/RELATIONSHIPS.md` is committed and diffable. Each **viewpoint** is a
bounded, readable domain (derived from the live FK graph, not hand-listed):

- a mermaid `erDiagram` of **enforced FKs only** → a missing relationship is a
  *visibly absent line*;
- a table of the viewpoint's **unenforced `*_id` gaps** → the absent lines, named.

v1 ships the **`stories`** viewpoint (`partner_stories` + its direct FK children
+ every `story_*` table): 32 tables, 36 enforced relationships, 20 unenforced
gaps. Add domains in the `VIEWPOINTS` array of `generate-schema-docs.mjs`.

### Optional: full `tbls` site

[`tbls`](https://github.com/k1LoW/tbls) (MIT) renders the **whole** schema as a
browseable per-table site, driven by `.tbls.yml` (whose `viewpoints:` tail is
generated by the same script). It runs via the `k1low/tbls` Docker image —
sourced through your registry mirror (`REGISTRY_PROXY`, same as the `infra/*`
Dockerfiles; `AISHA_TBLS_IMAGE` fully overrides) so nothing is pulled from Docker
Hub directly — output to `docs/db/tbls/` which is **gitignored**. Everything runs
locally against the local DB; the committed, readable ER is `RELATIONSHIPS.md`
(psql-only, needs no image at all).

## Per-story scoping

Stories are scoped by the explicit `*.story_id` FK fan-out (no polymorphic tag —
`story_labels` has none). The `stories` viewpoint is the FK closure around
`partner_stories`, so any new `story_*` table or any table that FKs into
`partner_stories` appears automatically on regeneration. A single story's
relationship neighbourhood is a filter over that same graph.

## Runbook

```bash
# Need an applied schema. Easiest: a throwaway pg17 left running.
AISHA_TYPEGEN_KEEP=1 npm run db:types:refresh:throwaway   # leaves a container up; note its URL
export AISHA_DB_URL=postgresql://postgres:postgres@127.0.0.1:<port>/postgres

# Enforce half
npm run db:schema:gaps:report     # list every candidate gap (never fails)
npm run db:schema:gaps            # gate: exit 1 on a NEW gap (this runs in cold-start)
npm run db:schema:gaps:baseline   # re-snapshot pre-existing gaps into the allowlist

# Visualize half
npm run db:schema:docs            # write docs/db/RELATIONSHIPS.md + .tbls.yml viewpoints
npm run db:schema:docs -- --tbls  # also render the full tbls site (Docker → docs/db/tbls/)
```

**Clearing a gap (the goal):** add a `FOREIGN KEY` in
`aisha/db/sql/tables/<table>.sql` (or `aisha/db/sql/constraints/` for cycle
breakers), regenerate baseline (`npm run db:init:generate`), re-baseline the
allowlist. **Keeping a gap intentionally** (cross-schema `auth.users` ref,
soft/polymorphic ref): leave it allowlisted with a real reason.

## Sibling DB-quality gates

The relationship lens has two siblings built from the same patterns (identity-keyed
allowlist · report/gate/baseline · the existing gate harnesses). Both came from
surveying purpose-built **DB** tools (not UML/design modelers).

### Migration safety — [Squawk](https://squawkhq.com) (static, no DB)

`scripts/db/check-migration-safety.mjs` lints `aisha/db/migrations/*.sql` for DDL that
locks or breaks prod — `CREATE INDEX` without `CONCURRENTLY`, dropping columns/tables,
renames, `NOT NULL` adds, FK adds without `NOT VALID`. Rule selection (prod-safety core;
operational/style noise excluded) is in `.squawk.toml`; pre-existing smells are snapshotted
in `migration-safety.allowlist.json` (identity = `file::rule::line`, migrations are
append-only). Runs in `test:gates` via `migration-safety.gate.test.ts`; Squawk is a pinned
devDependency. npm: `db:migrations:lint[:report|:baseline]`.

### Schema contract tests — [pgTAP](https://pgtap.org) (in-DB)

`aisha/db/tests/schema/*.sql` assert invariants the schema MUST satisfy — core tables,
PKs, columns, and the **enforced** relationships (`col_is_fk` / `fk_ok`) the lens verified.
This is the inverse of the gap allowlist: the allowlist tracks where FKs are missing, pgTAP
asserts where they must exist (add `fk_ok` lines as the inventory shrinks). `CREATE EXTENSION
pgtap` lives inside a rolled-back transaction, so pgTAP's ~700 functions never persist (and
never trip the definer-RPC gate); `infra/postgres` ships `postgresql-${PG_MAJOR}-pgtap`.
`scripts/db/run-schema-tests.mjs` parses the TAP output and is wired into
`verify-cold-start-apply.sh`. npm: `db:schema:test[:report]`.

## Files

- `scripts/db/check-fk-relationship-gaps.mjs` — the FK-gap gate (report/gate/baseline modes)
- `src/tests/gates/fk-relationship-gaps.allowlist.json` — pre-existing-gap snapshot
- `scripts/db/generate-schema-docs.mjs` — the doc/viewpoint generator
- `.tbls.yml` — tbls config (generated `viewpoints:` tail)
- `docs/db/RELATIONSHIPS.md` — committed per-domain ER + gap tables
- `.squawk.toml` + `scripts/db/check-migration-safety.mjs` + `src/tests/gates/migration-safety.{gate.test.ts,allowlist.json}` — migration-safety gate
- `aisha/db/tests/schema/*.sql` + `scripts/db/run-schema-tests.mjs` — pgTAP schema-contract tests
- `scripts/db/verify-cold-start-apply.sh` — wires in the FK-gap gate (step 5/5) + pgTAP step
