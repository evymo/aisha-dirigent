# Capability Gates — design spec

> **Status**: design adopted 2026-05-16. Implementation in progress.
> **Owner**: AISHA platform team. Co-designed with user (PR #7).

## Problem

The cold-start orchestrator deploys every service that appears in
`coolify/manifests/aisha.manifest`. Whether a deployed service can do
useful work is a runtime concern — discovered when the first request
fails with "provider not configured" / "missing client-secret" /
"upstream unreachable".

Three failure modes today:

1. **Silent fallback (`${VAR:-default}`)** — vestigial proxy defaults
   like `MCP_KNOWLEDGE_DOMAIN:-api.backend.id3a.cz` hide a real architectural
   question ("does openclaw have a knowledge source?") behind a default
   that *happens* to work today but locks topology choices in script
   boilerplate.

2. **Half-deployed stack** — `llm-gateway` deploys with
   `ANTHROPIC_API_KEY=${ANTHROPIC_API_KEY:-}` empty. Container is healthy,
   `/healthz` returns 200, but the *first chat request* dies with
   "no providers configured". The operator's only signal is a runtime
   500 from a dependent service (svc-ai-chat → llm-gateway).

3. **Dependent stack with broken provider** — `openclaw` deploys an
   AI-advisor service that calls into `llm-gateway`. If `llm-gateway`
   has no providers AND no local LLM (`vllm` / `ollama`) is present in
   the profile, the openclaw advisor is dead-on-arrival. Today it gets
   deployed anyway.

## Principle

> **No silent defaults except for numbered protocol bindings between
> stack components.** Configurable choices that affect *what the platform
> can do* must be either user-supplied, auto-generated by the cold-start,
> or **explicitly missing → service does not deploy**.

Numbered protocol bindings (OK to default):
- Internal ports: `POSTGRES_PORT=5432`, `RABBITMQ_PORT=5673`
- Docker network names: `coolify` (Coolify-managed external network)
- Internal service hostnames in shared compose network (DNS-resolved)
- Cryptographic algorithm parameters (`JWT_ALG=HS256`)

Configurable choices (NOT OK to default — capability-gated):
- External provider keys (`ANTHROPIC_API_KEY`, `OPENAI_API_KEY`, …)
- Optional infrastructure (Sentry DSN, Telegram bot token, …)
- Choice between local-only LLM (`vllm`, `ollama`) vs. cloud providers

## Schema

`config/services.json` per-service entry gains an optional
`capabilities` block:

```json
{
  "llm-gateway": {
    "role": "llm-router",
    "tier": "optional",
    "capabilities": {
      "requires_any_of": [
        { "external_key": "ANTHROPIC_API_KEY" },
        { "external_key": "OPENAI_API_KEY" },
        { "external_key": "GOOGLE_AI_API_KEY" },
        { "local_service": "vllm" },
        { "local_service": "ollama" }
      ]
    }
  }
}
```

Semantics:

- `requires_any_of: [{external_key}, {local_service}, …]` — service can
  deploy iff **at least one** alternative is satisfied.
- `requires_all_of: [...]` — service can deploy iff **every** entry is
  satisfied (used for hard dependencies — e.g. `pki` requires
  `keycloak` capability since pki-bridge needs JWKS).
- A `capabilities` block can mix both — `requires_all_of` must hold AND
  `requires_any_of` must have at least one satisfied entry.
- `external_key` checks if a key is non-empty in `.env-prod-backup` OR
  the operator's exported environment OR generated to `.env.coolify`.
- `local_service` checks if a service with that `id` is enabled in the
  current profile and would itself satisfy its capabilities (transitive).
- No `capabilities` block ⇒ service has no external dependencies and
  always deploys when included in the profile tier.

### Cascade semantics

If service A's `local_service` capability points at service B, and B is
itself disabled (either its capability gate fails or it is excluded by
profile), then A's capability gate transitively fails. The evaluator
walks the dependency graph once per cold-start.

Loops in `requires_*` are a hard error (gate test enforces DAG).

## Evaluation

`scripts/lib/eval-capabilities.mjs --profile=<id>` reads:

1. `config/services.json` (catalog with capabilities)
2. `config/profiles/<id>.json` (which services are included via
   `tier_filter` + `exclude` + `include`)
3. `.env-prod-backup` + `.env.coolify` + process env (external keys)

…and returns a structured report:

```json
{
  "profile": "cloud-multi",
  "services": {
    "core": { "enabled": true, "reason": "no capabilities required" },
    "llm-gateway": {
      "enabled": true,
      "reason": "satisfied by ANTHROPIC_API_KEY",
      "satisfied_by": [{"external_key": "ANTHROPIC_API_KEY"}]
    },
    "openclaw": {
      "enabled": false,
      "reason": "llm-gateway disabled (no providers configured)",
      "missing": [{"local_service": "llm-gateway"}]
    }
  }
}
```

CLI modes:
- `--shell` — emits `<SVC_ID>_ENABLED=true|false` exports for cold-start.
- `--json` — structured report (above).
- `--check` — exit 1 if any *required* service is disabled.

## Cold-start integration

`scripts/cold-start-doctor.sh` adds **Phase H — Capability gates**:

1. Run `eval-capabilities.mjs --profile=$AISHA_PROFILE --json`.
2. For each service marked `enabled: false`:
   - Tier `required` → **fatal** (block cold-start, doctor exits 1).
   - Tier `important` / `optional` → **warn** + record skip-list.
3. Cold-start uses skip-list when building manifest deploy waves —
   apps for disabled services are not created in Coolify.

`scripts/aisha-env-doctor.mjs` adds capability column to its summary:
external keys flagged "✗ missing" are cross-referenced against
capability rules — operator sees not just "key X empty" but
"key X empty ⇒ service Y disabled (alternative: configure Z or
enable vllm in profile)".

## AISHA UI surfacing

New RPC: `aisha_capabilities_status()` returns the same JSON as
`eval-capabilities --json` (server reads it from a cached file written
by cold-start). UI components consume via `useCapabilities()` hook:

```tsx
const { isEnabled, reason } = useCapabilities("llm-gateway");
if (!isEnabled) {
  return <FeatureDisabledBanner feature="AI chat" reason={reason} />;
}
```

This replaces today's pattern of catching 500s from disabled backends
with a UX-aware "configure ANTHROPIC_API_KEY in your Coolify env to
enable AI features" message.

## Vestigial `${VAR:-default}` audit

Once capability gates land, the following vars currently using `:-`
defaults need re-classification:

| Var | Current default | Correct disposition |
|-----|-----------------|---------------------|
| `MCP_KNOWLEDGE_DOMAIN` | `api.backend.id3a.cz` | **Remove entirely** — openclaw → core is a numbered dependency, use `${API_DOMAIN}` directly |
| `ANTHROPIC_API_KEY` | `""` (empty) | **Keep `:-`** — plumbing for `set -u` against operator-controlled `.env-prod-backup`. Capability gate decides deployment separately; this default is "treat absent declaration as empty value", not "silently mask missing feature". |
| `OPENAI_API_KEY` | `""` (empty) | Keep `:-` (same reasoning) |
| `GOOGLE_AI_API_KEY` | `""` (empty) | Keep `:-` (same reasoning) |
| `OPENCLAW_MATRIX_TOKEN` | `""` (empty) | Capability for openclaw notifications |
| `OPENCLAW_DISCORD_TOKEN` | `""` (empty) | Capability for openclaw notifications |
| `RESEND_API_KEY` | `""` (empty) | Capability for outbound email (gotrue / svc-ai-chat) |
| `SENTRY_DSN` | `""` (empty) | Capability for observability + UI error reporting |
| `IMAGE_LLM_GATEWAY` | `cache.aisha.guru/theopenco/llmgateway:v0.5.0` | **Keep** — numbered binding (pinned image tag) |
| `IMAGE_OPENCLAW` | `cache.aisha.guru/openclaw/openclaw:latest` | **Keep** — numbered binding |
| `OPENCLAW_MAX_PARALLEL_AGENTS` | `3` | **Keep** — operational tunable, sensible default |
| `OPENCLAW_SANDBOX_CPU_LIMIT` | `0.5` | **Keep** — operational tunable |
| `OPENCLAW_OIDC_CLIENT_ID` | `openclaw` | **Keep** — numbered binding (KC client id) |
| `OPENCLAW_MATRIX_HOMESERVER` | `https://${MATRIX_DOMAIN}` | **Keep** — numbered binding (which matrix server) |

Rule of thumb: if the default is *what makes this part of the stack
work given the rest of the stack exists*, it stays. If the default is
*what masks the absence of a thing*, it's a capability gate.

### `${VAR:-}` for `set -u` plumbing vs. `${VAR:-default}` for hiding gaps

A subtlety: under `set -uo pipefail` (cold-start mode), referencing a
declared-but-empty var is allowed, but referencing an UNDECLARED var
aborts. The pattern `${ANTHROPIC_API_KEY:-}` is *plumbing* for the case
where `.env-prod-backup` literally omits the line — it says "treat
omission as empty value". The capability gate then decides whether
empty is acceptable. This is OK and is **NOT** what we mean by "silent
default".

What IS a silent default:
- `${MCP_KNOWLEDGE_DOMAIN:-api.backend.id3a.cz}` — masks the question
  "does openclaw have a knowledge source?" behind a value that
  *happens* to point at the right place today. **Removed in PR #7.**

The test for whether a `:-` belongs:
- Empty operator input + no capability gate ⇒ runtime mystery error ⇒
  remove `:-`, add capability gate.
- Empty operator input + capability gate decides deployment ⇒ `:-` is
  fine; gate is the actual control point.

## Out of scope (future work)

- Per-tenant capability overrides (some tenants get email, some don't)
- Cost-aware capability ranking (prefer cheapest satisfied alternative)
- Dynamic capability re-evaluation (post-deploy if a key gets added)

## Implementation phases

- **Phase 1** (this PR): schema + evaluator + gate tests, no behavior
  change yet. Capability declarations added to llm-gateway + openclaw.
- **Phase 2** (next PR): cold-start preflight integration (Phase H).
- **Phase 3** (next PR): AISHA UI capability surfacing.
- **Phase 4** (cleanup): remove vestigial `:-default` lines, gate test
  forbids re-introduction.
